# 方寸裡的生肖 — 資訊架構與資料模型（設計規格）

- **status**: proposed
- **version**: 0.1.0
- **來源**: 由 Obsidian vault 設計筆記「方寸裡的生肖」搬遷整理而成（ADR 式決策紀錄）。

---

## 背景與定位 (Context)

目標是建立一個關於生肖郵票的網站。經討論後，定位由「個人收藏展示館」收斂為
**科普／參考站**：內容不限於自有藏品，而是涵蓋各郵政發行的生肖郵票，追求
資料的完整度與正確度。

此定位轉變帶來的核心挑戰，從「呈現」變成 **資料蒐集與查證**——能否被當作可引用
的權威來源，才是這個站的價值所在。

## 考量因素 (Decision Drivers)

- 參考站的公信力取決於資料正確度與來源可追溯性。
- 跨多個發行地（台、中、港、澳、日、美…），資料來源分散且彼此存在出入。
- 維運者時間有限，需避免高頻人工維護的負擔。
- 偏好結構化輸出（JSON/CSV）、單一資料來源驅動的架構。

## 決策 (Decisions)

### D1 — 定位為科普／參考站
不以自有藏品為主體，改以「發行資料庫」為核心。藏品僅作為加值的故事性專題。

### D2 — 資料模型驅動（single source of truth）
以一份結構化資料（JSON/CSV）為唯一資料來源，網站由它生成。新增年份或勘誤
只改資料、不動版面。資料同時開放下載（見 sitemap `/data/`）。

### D3 — 資訊架構（Sitemap v0.1）

```
/                          首頁：定位說明 + 精選專題 + 三種入口（生肖/發行地/年份）
│
├─ /about/                 認識生肖郵票（導論）
│   ├─ 什麼是生肖郵票、票種源流（日本1950虎票 → 台灣1968雞票）
│   ├─ 干支與十二生肖基礎
│   └─ 重要觀念：發行年 ≠ 生肖年（賀歲票於前一年底發行）
│
├─ /catalog/               郵票資料庫（網站主體，可篩選索引）
│   ├─ /zodiac/{animal}/    依生肖（12 個 landing：鼠牛虎兔龍蛇馬羊猴雞狗豬）
│   ├─ /region/{code}/      依發行地（TW / CN / HK / MO / JP / US …）
│   ├─ /timeline/           依年份時間軸
│   └─ /issue/{id}/         單筆發行詳情頁（核心模板）
│
├─ /features/              主題專題（有故事性的深度文）
│   ├─ 1980 庚申年猴票的傳奇
│   └─ 世界第一套雞票：台灣 1968
│
├─ /guide/                 集郵入門
│   ├─ 術語（小全張/小型張/首日封/四方連…）
│   └─ 保存與辨識基礎
│
├─ /about-site/            關於本站（參考站的公信力來源）
│   ├─ 編輯方針與資料來源分級說明
│   └─ 勘誤回報
│
└─ /data/                  開放資料下載（JSON / CSV）— 選配
```

`/about-site/`（編輯方針與勘誤）是參考站與一般部落格的分水嶺，務必保留；
`/data/` 公開單一資料來源，對 SEO 與公信力皆有加分。

### D4 — 資料 Schema v0.1
核心實體為「一套發行」（Issue），底下掛多個「品項」（Item，含郵票與小全張等）。
來源（Source）獨立維護並分級。詳細欄位定義見 [`data-model.md`](./data-model.md)。

### D5 — `zodiac_year` 與 `issue_date` 永遠分離
賀歲票於生肖年的前一年底發行，故「發行年」與「生肖年」常差一年。
排序與時間軸一律使用 `issue_date`；生肖歸類一律使用 `zodiac` / `zodiac_year`。
兩者永不混用。

### D6 — 來源分級與查證標記
每筆 Issue 透過 `sources[].ref` 連到分級過的 Source；`tier` 區分一手官方／權威
目錄／二手來源，`verified` 標記是否經查證。這是全站公信力的骨幹。

### D7 — Facebook 粉絲頁策略
不投入日更。粉絲頁定位為「網站的擴音器」，綁定**年度賀歲票發行季**（約 11 月至
隔年 1 月）密集發文，平時低頻。初期亦可先借既有集郵社群驗證內容，再決定是否
自建頻道。

### D8 — 非生肖藏品：另立「我的收藏」展示區，不進核心資料庫
收藏中有相當部分非生肖票（古畫、特殊形狀、特別事件如棒球奪冠／郵務週年等），與
生肖參考資料庫**本質不同**，不併入核心 `/catalog/`：

| | 生肖參考資料庫 | 我的雜項收藏 |
|---|---|---|
| 性質 | about the world | about me |
| 目標 | 完整、可查證、可被引用 | 展示、故事性，**不求完整** |
| 資料模型 | 重（zodiac／來源分級／verified…） | 輕（圖＋主題＋一句話） |
| 價值來源 | 權威性 | 個人品味 |

處置：核心維持 D1–D6；另設 `/collection/`（畫廊式、輕量、獨立資料模型）；視覺明確
區隔；名稱不改。**排程：列為 v2**，先把生肖參考站做好。

### D9 — 技術選型：Astro（靜態網站）
採 **Astro** 建置靜態網站，部署於 GitHub Pages 或 Cloudflare Pages。

選擇理由：
- 本站核心價值與風險是「資料正確、可被引用」（D1／D6），而非版面或重互動。
- Astro 的 **Content Collections + Zod** 把 D4 schema 與 D6 查證骨幹變成 **build-time
  保證**：欄位漏填、`tier` 拼錯、型別不符即 build 失敗，零額外工具達成。
- 結構化資料是一等公民；詳情頁與三軸索引用 `getCollection()` + `getStaticPaths()` 生成。
- 預設零 JS、SEO 佳；`/about/`、`/features/`、`/guide/` 以 Markdown 撰寫。
- 既有專案「共和曆」前端即為 Astro（`~/works/gongheli/web`）。

取捨：曾評估 Hugo（taxonomy 讓三軸索引近乎免費、build 更快），但**缺內建 schema
驗證**，需自行加 CI。本站正是「結構化資料＋正確性掛帥」，故選 Astro。

## 結果與取捨 (Consequences)

**正面**
- 資料與呈現解耦，維護成本低，且利於開放資料與 SEO。
- 來源可追溯，具備被引用為參考來源的條件。
- 發行年/生肖年分離，從源頭杜絕時間軸錯位。

**代價／風險**
- 跨地區資料蒐集與查證工作量大，是專案最大的隱性成本。
- 來源彼此存在出入（如輪次與套數的說法不一），需建立勘誤與覆核流程。
- `items` 採陣列雖具彈性，前端需處理可變數量的渲染。

## 已查證事實（種子資料來源）

> 以下為已查證、可直接寫入 `/about/` 與首批 Issue 的事實。對應的結構化資料見
> `src/content/catalog/`，來源見 [`sources.md`](./sources.md)。

- 票種源流：1950-02-01 日本以虎年發行世界第一套生肖郵票。[來源 6]
- 台灣首套：郵政總局於民國 57 年（1968）11 月 12 日發行雞票，為世界第一套
  雞年生肖郵票，發行 50 萬套。[來源 4]
- 中華郵政自民國 57 年起發行新年郵票，以新歲值年生肖為主題，每 12 年一輪，
  俗稱生肖郵票。[來源 1、4]
- 發行時序：賀歲票於前一年底發行次年生肖票（首套雞票 57 年 11 月發行，
  58 年才是雞年）。[來源 4]
- 民國 57 年至 80 年（1968–1991）共發行 24 套，正好完成 2 輪十二生肖循環。[來源 3]
